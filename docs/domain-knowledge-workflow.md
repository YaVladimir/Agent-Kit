# Фаза 4: сбор доменного знания

Этот runbook описывает безопасный ручной workflow для превращения знаний
продакт-овнера и техлида в `.context/glossary.yaml`,
`.context/processes/*.yaml` и `.context/rules/*.yaml`.

Скрипты kit не записывают аудио, не транскрибируют и не вызывают внешние API.
Если команда использует Whisper или другую транскрибацию, инструмент должен быть
установлен только из approved внутреннего источника.

## Цель

После заполнения `.context` агент должен принимать задачу на бизнес-языке и
через `domain.translate_task` получать:

- бизнес-термины и синонимы;
- релевантные процессы;
- применимые правила;
- маппинг на классы, методы, endpoint'ы и тесты;
- первичный план проверки точек изменения через code/LSP/architecture tools.

## Участники

- Продакт-овнер: объясняет процессы, правила и исключения.
- Техлид: добавляет маппинг терминов на код и проверяет технические границы.
- Разработчик внедрения: поддерживает YAML, схемы и MCP-проверку.
- Ревьюер домена: подтверждает, что `.context` не содержит секретов и PII.

## Сессии с продакт-овнером

Используй `templates/domain-interview.md` как основу.

1. Карта домена: основные термины, роли, продукты, статусы и события.
2. Основной процесс: happy path, альтернативные сценарии, ошибки и SLA.
3. Правила и исключения: лимиты, комплаенс, регуляторика, ручные решения.

После каждой сессии подготовь черновик YAML и отправь на асинхронное ревью.

## Extraction

Используй `prompts/domain-extraction.md` для структурирования транскрипта или
заметок в YAML. Результат считается черновиком: агент не должен сам принимать
его как истину без ревью продакта и техлида.

Минимальные артефакты:

- `.context/glossary.yaml`
- `.context/processes/<process-id>.yaml`
- `.context/rules/<domain>-rules.yaml`
- `.context/domain-intake.md`

## Ревью техлида

Техлид обязан проверить:

- каждый термин имеет понятное бизнес-описание;
- у важных терминов есть `code.modules`, `code.classes` или `code.methods`;
- у процесса есть `entrypoints`, `services`, `tests`;
- правила с риском для продукта имеют `code` и `tests`;
- нет секретов, персональных данных и внутренних URL с токенами.

## Definition of Done

Для задачи, меняющей бизнес-логику, PR считается полным только если:

1. Изменения в коде подтверждены tests или явным объяснением, почему тестов нет.
2. Если изменился термин, процесс или правило, обновлён соответствующий `.context`.
3. `domain.translate_task` для ключевой формулировки возвращает релевантные
   change points.
4. Если изменился endpoint или слой, обновлён `.context/architecture-graph.yaml`.
5. Ревьюер подтвердил отсутствие секретов и PII в контексте.

## Quarterly review

Раз в квартал команда проверяет:

- устаревшие процессы;
- правила, связанные с инцидентами и дефектами;
- маппинг на переименованные классы и endpoint'ы;
- зоны, где агент ошибался при планировании.

Результат review коммитится как обычное изменение `.context`.
