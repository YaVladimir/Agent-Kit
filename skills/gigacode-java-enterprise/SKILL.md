# GigaCode Java Enterprise

Используй этот skill при работе с корпоративными Java-репозиториями, где агент
должен понять бизнес-термины, границы модулей, существующие паттерны и тесты до
изменения кода.

Общайся на русском языке по умолчанию. На русском пиши переформулировки задач,
планы, промежуточные статусы, финальные ответы, ревью-заметки, новую
документацию и новые поясняющие комментарии, если стандарт репозитория не требует
другого языка. Идентификаторы, команды, логи, HTTP-маршруты и публичные API не
переводи.

## Рабочий сценарий

1. Переформулируй задачу простыми словами.
2. Определи тип задачи: бизнес-изменение, багфикс, рефакторинг, тесты,
   инфраструктура, документация или ревью.
3. Если в задаче есть бизнес-термины, сначала используй доменный контекст.
4. Прочитай сводки репозитория и модуля до выбора точек изменения.
5. Используй LSP/MCP для поиска символов, определений, использований,
   реализаций, diagnostics и тестов.
6. Найди похожие реализации и переиспользуй локальные паттерны.
7. Перед нетривиальной правкой покажи короткий план.
8. Меняй только файлы, необходимые для задачи.
9. Запусти самые узкие осмысленные проверки; расширяй их, если затронуто общее
   поведение.
10. Сообщи изменённые файлы, проверки, оставшиеся риски и ручные проверки.

## Порядок инструментов

Для бизнес-изменений предпочитай такой порядок:

1. `domain.lookup_task(query)`
2. `context.repo_overview()`
3. `context.get_module_summary(module)`
4. `code.search_symbols(query)`
5. `code.read_definition(symbol)`
6. `code.find_references(symbol)`
7. `code.find_tests(symbol)`
8. `architecture.check(files)`

Если инструмента нет, продолжай ближайшим локальным способом: LSP, `rg`, файлы
сборки, имена тестов или `.context` файлы.

## Правила планирования

Перед реализацией определи:

- какое бизнес-правило или баг меняется;
- какие точки входа и сервисы участвуют;
- какой существующий сервис, метод или annotation нужно переиспользовать;
- какие тесты вероятнее всего добавить или обновить;
- какие есть архитектурные риски и границы владения.

Спрашивай разработчика только тогда, когда остаётся несколько продуктовых или
архитектурных вариантов.
